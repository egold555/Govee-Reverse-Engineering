Christmas tree string light, 250/375 individually addressable LEDs. Control is over
**encrypted BLE**, the same scheme that stopped the [H61F6](H61F6.md) work. The
encryption is broken here: the handshake key is the fixed string " MakingLifeSmarte", and the
session key is sent in the light's first reply. That gives **per-LED color**, through the "DIY" drawing command.

Reference code (Python, `bleak` + `cryptography`):
[govee_strip.py](https://github.com/BennoCrafter/xmas-mapper/blob/main/src/govee_strip.py)
(driver and CLI),
[pklg_decode.py](https://github.com/BennoCrafter/xmas-mapper/blob/main/scripts/pklg_decode.py)
(decrypts Apple PacketLogger `.pklg` captures of the Govee Home app).

### Checklist of packets
- [x] Handshake / session key (`e7 01`, `e7 02`)
- [x] Keepalive (`aa`)
- [x] Per-LED DIY drawing, any number of LEDs (`a4`)
- [x] Switch to DIY mode (`33 05 0a`)
- [x] Whole-strip color (`33 05 15 01`)
- [x] DIY effects: Twinkle, Fade, Breathe, plus speed, brightness and background
- [x] Power on / off (`33 01`)
- [x] Brightness outside DIY (`33 04`)
- [x] A "static / no effect" DIY code does not exist. Fade at speed 0 is used instead as static
- [ ] `33 09 …` sent on connect, meaning unknown
- [ ] `ab …` device info, `ee …` status from the light: seen, not decoded

## GATT

```
write     00010203-0405-0607-0809-0a0b0c0d2b11   write without response
notify    00010203-0405-0607-0809-0a0b0c0d2b10
```

Same UUIDs as the plain `0x33` devices. The difference is that every payload,
both directions, is encrypted. Only one client can be connected, so **quit the
Govee app** first.

## Encryption

Every packet is encrypted the same way. The key is
`MakingLifeSmarte` (ASCII, 16 bytes) for the handshake and the session key after it.

```
n = len(data) // 16 * 16
cipher = AES-128-ECB(key, data[:n]) + RC4(key, data[n:])
```

- Full 16-byte blocks use AES-128-ECB.
- The leftover tail (1–15 bytes) is XORed with RC4 keyed with the **same** key.
  RC4 restarts **for every packet**, so there is no stream state to track.
- Decryption is the same, with AES decrypt instead of encrypt (RC4 is symmetric).

So a 20-byte command is one AES block plus 4 RC4 bytes. Identical plaintext gives
identical ciphertext within a connection. This matches what the H61F6 notes
observed: no per-message counter, but a key that changes per connection.

### Plaintext framing

Every plaintext ends with an **XOR checksum** of all bytes before it. Short
commands are padded with `00` to 19 bytes, then the checksum is added (20 bytes).
DIY packets are variable length and not padded.

A checksum that matches after decryption is the easiest way to know the key is right.
The decoder uses that to tell whether a packet was sent with the fixed key or the
session key.

### Handshake

```
TX  e7 01 <17 random bytes> <xor>     encrypted with MakingLifeSmarte
RX  e7 01 <16-byte session key> ...    encrypted with MakingLifeSmarte
TX  e7 02 <17 random bytes> <xor>     encrypted with MakingLifeSmarte
RX  e7 02 ...                          encrypted with MakingLifeSmarte
```

From here on, everything uses `session key = reply[2:18]`. The random bytes the
app sends do not seem to matter.

### Keepalive

`aa 00 …` (padded, checksum `aa`) about every 2.5 s, the light echoes `aa …`.
The app sends it the whole time, so the driver does too.

## Per-LED control: DIY drawing

A drawing is a list of color groups, each with the LED indices it lights. LEDs that
are not listed show the background color. All multi-byte numbers are **little endian**.

```
a4 00 00                 part number (see "Splitting")
01 <parts> 00 03         <parts> = number of a4 packets, the empty last one included
<effect> <speed> <bri>   effect code, speed 0-100, brightness 1-100
<bg R G B>               background color, "off" = 01 01 01
<groups u16>
  per group:
    <count u16>          total LEDs in this group
    <R G B>
    <high u16>           how many of them are >= 256
    <index u8> ...       indices < 256, one byte each   (count - high of them)
    <index u16> ...      indices >= 256, two bytes each (high of them)
<xor>
```

Effect codes seen so far:

| Code | Effect  |
|------|---------|
| `0f` | Twinkle |
| `13` | Fade    |
| `14` | Breathe |

The app never sends black `00 00 00`. It uses `01 01 01` for "off", so do the same.

### Splitting
This was the real pain in the ass.

The app splits a drawing into packets of at most **505 bytes**. Each part is one
BLE write:

```
a4 00 00 <data> <xor>     first part
a4 01 00 <data> <xor>     middle parts, numbered 01 00, 02 00, …
a4 ff ff <data> <xor>     last part, always sent, even when empty
```

`<data>` is the drawing above without its own `a4 00 00` and checksum, cut into
501-byte pieces. Each part has its own checksum. The `<parts>` byte in the header must
match the number of parts sent: the light only draws as many as it announces.

The app keeps drawings short by choosing a background color. With the most common
color as the background, most LEDs do not need to be listed. Because indices ≥ 256
cost two bytes, the best background is the one that gives the shortest packet,
which is not always the most common color.

### Apply

After the last `a4 ff ff` part, send:

```
33 05 0a 20 03 03 00 … <xor>
```

The light replies `a4 03` (drawing received) and `33 05` (mode set). You can send all
parts and the apply back to back, then read the replies. For animation you can also
start the next frame before the previous replies arrive, which is about twice as fast.

## Other commands

All are 20 bytes: padded with `00`, then the XOR checksum.

| Plaintext | Meaning | Reply |
|---|---|---|
| `33 05 15 01 RR GG BB 00 00 00 00 00 ff 7f` | Whole strip one color (leaves DIY mode) | `33 05` |
| `33 01 01` / `33 01 00` | Power on / off | `33 01` |
| `33 04 <1-100>` | Brightness | |
| `33 09 …` | Sent by the app on connect, unknown | |
| `ab …` | Device info request, the reply holds device identifiers (credential) | `ab …` |
| from light: `ee …` | Status, not decoded | |

The same AES + RC4 scheme and `MakingLifeSmarte` key are worth trying on other
devices that answer only to ciphertext, such as the H61F6.
